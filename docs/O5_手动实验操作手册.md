## 1. O5 要验证什么

课程原要求：用 HAProxy 或 Nginx 替换 lbd，配置健康检查，重做 C1、C3，比较两者的检出时间与配置方式。本组选择 HAProxy，不要求重做 C2。

O5-C1 重做 kill 与 pause：看 HAProxy 何时将实例判 DOWN、何时恢复 UP、期间客户端受多大影响。O5-C3 把一个实例降配到 13%：看业务延迟增加时，就绪健康检查是否仍然通过，并和 C3 的普通检查、离群摘除对照。

检验机制比得到某个“更好”的结果更重要。健康检查没有发现变慢、仍然没有超过 200ms，都可以是符合机制的结果。

原 lbd 的 8080/8090 继续供 scaler 登记后端和读取就绪状态。HAProxy 静态配置三个端口，各自进行健康检查，不接收 scaler 的删除命令。保留这条控制路径是为了沿用原 scaler 的补建、预热和生命周期记录，不需要修改队友代码。

## 6. 看懂 HAProxy 配置

```bash
cat deploy/haproxy-o5.cfg
haproxy -c -f deploy/haproxy-o5.cfg
```

最后一条只验证配置，应显示 `Configuration file is valid`；不会启动负载均衡服务。

| 配置项 | 本组设置 | 含义 |
|---|---|---|
| frontend bind | 127.0.0.1:18081 | O5 客户端入口，只监听本机 |
| backend servers | 8101、8102、8103 | 直接转发到三个应用实例 |
| balance | roundrobin | 轮询分发 HTTP 请求 |
| http-check send | GET /readyz，Host localhost | 探测应用就绪接口 |
| http-check expect | status 200 | 明确要求响应码 200 |
| inter / fastinter / downinter | 均为 1s | 正常、过渡、不健康状态下的检查间隔 |
| fall / rise | 3 / 2 | 连续失败三次 DOWN，DOWN 后连续成功两次恢复 |
| timeout connect / check | 均为 500ms | 连接阶段和连接后的探测等待时间分别限制 |
| timeout server / client | 均为 2s | 对应方向的无活动超时；与客户端整体超时不是完全相同的概念 |
| retries / retry-on | 0 / none | 禁止自动重试掩盖故障窗口 |
| nbthread / AllowedCPUs | 2 / 0–1 | HAProxy 两个线程、绑定控制和压测使用的核 |

HAProxy 2.8 默认初始 UP，脚本等待三台均真实检查 L7OK、稳定 UP 两秒后才开始压测。配置没有按业务 p99 的离群摘除，也没有按错误的被动摘除。`fall/rise` 是检查次数，不是秒数；实际检出时间还受探测相位、耗时和调度影响。

## 19. 中断或检查失败时

脚本对 Ctrl+C、SSH HUP、TERM 尝试停止本次 loadgen，恢复被暂停的 8103、将 C3 的 8102 恢复 25%。自动模式会关闭它自己启动的 HAProxy；手动模式保留已有 HAProxy。SIGKILL、主机断电等无法保证执行清理，因此重连后先检查实际状态。

出现 ABORTED.json 的目录是未完整完成的运行，不能当作正式结果。已有目录保留，不会自动重跑覆盖。


## 20. 答辩时需要解释的四点

第一，替换发生在业务路径：请求进入 HAProxy，再直接到应用；原 lbd 的作用变成给 scaler 保留控制接口。

第二，kill 与 pause 不同：kill 让进程退出，scaler 会补建；pause 保留进程但停止响应，更能检验主动健康检查。HAProxy 配置三个静态端口，不接收 scaler 的删除通知。

第三，健康检查关心 `/readyz` 是否及时返回 200；轻量接口成功不保证真实业务的 p99 正常。HAProxy 普通主动检查与 lbd 的业务延迟离群摘除是不同机制。

第四，报告检出时间必须明确来源：marks 的实际注入时刻，到 HAProxy 首次 DOWN 的采样观测；200ms 是目标采样间隔，真实最大间隔在 observer-meta.json。内部转换的保守区间取“上次采样请求开始，到这次采样响应结束”，把 Runtime API 自身耗时也纳入。不能把采样时间或 journal 接收时间叫作内部精确事件时刻。
